# KBOL choices on the KB-DPP schema

The KB-DPP 1.0 contract (core and implementation, in [reference](reference/)) fixes types, states, transitions, events, relations, digest and errors. Some shapes it leaves open. This document records how KBOL settles them, with the reason and the condition for revisiting each one, following the implementation guide's "Choices register". None lowers a requirement of the contract. They apply equally to any project that adopts KBOL; what belongs to each installation (roles, people, repository and branch) lives in that installation.

## Fields and shapes

| Choice | What the contract fixes | Concrete form | Reason | Revisit if |
|---|---|---|---|---|
| Date of a fact | "date or interval of the claim, with its precision" | `date` (date or instant) or `interval: {from, until?}`, one of the two, and `precision` in `instant`, `minute`, `hour`, `day`, `month` or `year` | `precision: day` appears in the guide for legacy data; the rest follows that shape | A fact needs uncertainty that is not rounding |
| Approval rule | `one`, `all` or `quorum` with an explicit integer | `"one"`, `"all"` or `{quorum: N}` with N ≥ 1 | The quorum carries its number in the same value and a quorum without a figure is not admitted | Rules per scope within the role are needed |
| Position of an addition | "explicit logical position" | Field `position` (text) in the `amends` object, mandatory in an addition and forbidden in the others | The identity of the clause does not depend on numbering | Consolidation needs a structured position |
| `by` of an amendment | Identifies the new clause of the amending record | Must start with the ID of the record itself and exist in its body | Prevents a decision from replacing with someone else's text | — |
| `verified` | Positive events bound to the digest of the verified content | List of `{by, at, digest}` | Without the digest, an old `verified` would look current after the content changed | Full compatibility with OKF 0.2 is adopted |
| `generated` | `{by, at}` | Same, with `at` an instant with time zone | — | — |
| Quality of a derivation | Dimensions with method, result and limits; explicit `not_evaluated` | Map dimension → `{method, result, limits}` or `"not_evaluated"`; `result` in `conforming`, `non_conforming`, `partial`, `not_evaluated` | Reuses the enumeration of evaluations | The pilot ingestion asks for another scale |
| Tolerances of a milestone | Limits of time, cost, resources and scope; absent is not unlimited | Object with those four optional keys, each text or object | Inheritance from the delegation is resolved at execution, not in the schema | The executor needs numeric limits |
| `timeout` of a check | Exact integer | Seconds, integer ≥ 1 | Usual unit of command runners | — |
| AI-assisted evaluation | Requires a rubric and a human criterion for resolution | Fields `rubric` and `disagreement_resolution` in the acceptance criterion | — | — |
| `vetoes` | Pattern engine fixed by version, no arbitrary code | `pattern` is a literal term; regular expressions are not admitted | A literal pattern executes nothing and is predictable | A veto needs morphological variants |
| `owner` of a question | No fixed shape | ID of a role or a person | It is the person or role that must close it, not a name | — |
| Evidence of an event | "mechanism and proof" | `event_evidence: {mechanism, proof}` | — | — |
| Proof of an approval | Checkable against a trusted service | Non-empty text or object; checking it is the job of the integration gate | The schema cannot verify it | An approval channel other than GitHub is added |

## Identity

New IDs are `<PREFIX>-<UUID v4>`, as the contract fixes. Also accepted are those of the default legacy format (`ADR-NNNN`, `QD-nnn`, `HD-nnn`, `PL-nnn`, `PL-nnn-Hk`) and, with a contract prefix, short IDs of the test corpus such as `DEC-A` or `SRC-AR2`, which the contract scenarios admit as legacy. The prefix must match the type of the record. Since the contract admits short IDs in its test corpus, the schema does not yet require a UUID for a new record; that requirement comes with the integration gate, which tells a created record from a legacy one by comparing with the base.

Text patterns end in `(?!\n)$` and not in `$`: in Python, `$` admits a final line break, so `DEC-A` and `DEC-A\n` would validate as different IDs that look the same. The chosen form is also valid in ECMA-262, the JSON Schema dialect.

## Reading the header

Besides repeated keys and object-construction tags, which the contract forbids, any explicit tag is rejected, including the non-specific `!`, as well as anchors, aliases and merge keys. None is needed in a record and all of them allow the value read to differ from the one seen. Unquoted dates are read as text: PyYAML would turn them into `date` and lose precision. Values YAML 1.1 turns into booleans (`no`, `yes`, `on`) are rejected by the schema where text is expected.

## Digest

The contract excludes from the approvable object the events, projections, caches, receipts, `verified`, evaluations and references to the approval. These are read as the projections `state` (materialised from the events), `status` and `stale_after` (computed by a policy). No field is removed by heuristics. The requested effects are a list of transitions with `new_state` and `valid_from` (instant with time zone), and optionally `previous_state` and `valid_until`; any other field, such as a `recorded_at` not yet known, is rejected. No decimal value enters the object, not even `600.0`. The eleven published vectors are in `kbol/vectors/digest.json`, including the contract's literal example, extracted from its text. The minimal vector was checked with `sha256sum` over hand-written bytes; there is no second adapter yet that reproduces them.

## Validation modes

`proposal` rejects undeclared fields, requires clauses in a decision and, if there are no events, requires the initial state of the type: a change of state is requested as an effect, not written. `canonical` requires an admitted history: no local events (`recorded_at` null), a chain that starts with `creation` or `import`, transitions from the table, increasing `recorded_at` and the written state equal to the materialised one; also, accepting a decision needs a prior ratification that has not been revoked. `exchange` keeps undeclared fields with a warning. No mode checks the authenticity of `event_evidence` or of the ratification: the integration gate does that.

## Projection

`status` is computed only from admitted events. A record without admitted history has no projection (`None`, with a warning), and a successor without history supersedes nobody. When a date with day precision makes validity ambiguous, the projection does not fail: rule 3 gives `draft` and an ambiguous successor does not count, in both cases with an `AMBIGUOUS_TIME` warning.

## Body

A code fence must be separated by a blank line from the `<clause>` mark that precedes it: without it, CommonMark absorbs it into the HTML block and its marks are interpreted. A mark inside a quote (`> <clause …>`) is not interpreted. Inline code does not cross a blank line.

In the snapshot, an anchor whose body was not loaded stays as a coverage warning, with a null code, instead of being taken as valid.

## Dry-run migration of a legacy format

`kbol.migration` is the read adapter for an OKF format older than the contract's: Markdown records with a YAML header, `type` in prose ("Decision", "Question"…) and IDs `ADR-NNNN`, `QD-nnn`, `HD-nnn`, `PL-nnn` and `PL-nnn-Hk`. It is the default legacy format. A project with the same shape and other IDs or state words declares it in its installation (below, "Legacy format of another project"), and one with another format would need its own adapter. The proposed import event carries neither `recorded_at` nor `event_evidence`: integration adds them. Its `valid_from` is the legacy `date` with `precision: day`, without turning it into an instant. Since it is not known in which time zone that day started, a validity query less than 14 hours from its UTC midnight returns `AMBIGUOUS_TIME`. Authority written in prose (`adopted_by`, `approved_by`) is classified as `pending` or `insufficient`, never as checked.

| Legacy state | Proposed state | Human review |
|---|---|---|
| Decision Proposed, Accepted, Rejected | proposed, accepted, rejected | Yes if the acceptance has no checked authority |
| Decision "Accepted; partially superseded by…" | accepted | Yes: anchors and reach of `amends` |
| Decision "Superseded by…" | accepted | Yes: `supersedes` is written in the successor |
| Question Open, Discarded | open, discarded | No |
| Question "Resolved (ADR-n)" | resolved, with a candidate `resolved_by` | No |
| Question "Resolved (fact: …)" | resolved | Yes: the source or the fact is missing |
| Question "Under review" | open | Yes |
| Hypothesis Open, Under validation, Validated, Discarded, Obsolete | open, open, validated, retired, retired | Yes except Open |
| Plan Proposed, Approved, Closed | proposed, authorized, closed | Yes unless Proposed |
| Plan In progress | authorized | Yes |
| Plan Rejected, Abandoned, Superseded | cancelled | Yes |
| Milestone Pending | proposed | Yes: the authorization of the milestone is not on record |
| Milestone In progress, Done | in_progress, completed | Yes: authorization and acceptance per criterion |
| Milestone Discarded | cancelled | No |

The dry-run migration does not translate legacy fields that have no destination in the new schema (for example `branch`, `evidence`, `origin`, `kind` or `answers`): their translation is semantic and is left to the migration of the corpus.

### Legacy format of another project

A project may write its records with the same `type` labels and the same state prose as the default format, but with IDs `DEC-nnn`, `Q-nnn` and `H-nnn`, other state words (for example the Spanish "Vigente") and headers closed also by a period or a comma ("Open. Announced on…"). Its installation declares it in `legacy_format`, which `--installation` brings to `migrate`, to the queries and to `context`:

```json
"legacy_format": {
  "records": {
    "Decision": {"type": "decision", "id": "DEC-\\d{3,}", "equivalences": {"Vigente": "Accepted"}},
    "Question": {"type": "question", "id": "Q-\\d{3,}"},
    "Hypothesis": {"type": "hypothesis", "id": "H-\\d{3,}"}
  },
  "separators": "(;.,"
}
```

| Piece | Choice | Why |
|---|---|---|
| Reach | The declared format fully replaces the default format; without declaring it, reading is as before | A project does not accept another project's IDs as its own legacy records |
| `id` | Pattern that the whole ID of a record with that label must match; it starts with a literal prefix, and a contract prefix must be the one of the declared type | `Q-087` cannot be a hypothesis, because the prefix `Q` already imposes the question type |
| Record without `id` | Counts as a record, and leaves the load partial, if its name is an ID of the format followed by `.md` | Like the record name of the default format: what could be a record is not skipped |
| `equivalences` | Project state word → header of the table above, applied to the word the state starts with; then the table decides | "Vigente; partially superseded by…" keeps the review of `amends`. A direct equivalence to a contract state would silently lose those rules, and the installation does not invent states |
| `separators` | Characters that close the header; by default, parenthesis and semicolon | In the default format "Open. …" has no mapping, and changing it would change how it is read |
| `resolved_by` | The candidate of a resolved question comes first from the `resolved_by` field of the legacy record, if it has one, and then from the state text; only decision IDs of the format count | Some formats write the decision in the field and not always in the state |
| Error | A malformed declaration stops the command without reading anything: `INVALID_SCHEMA` in the queries and in `migrate` | Reading with a half-declared format would report as invalid records that are not |

Integration and import still read only the default format: with another format, KBOL queries, it does not migrate. Revisit if: a format needs a state rule the table does not have, or a project with a declared format asks to import its legacy records.

### Compatible reading during the transition

The contract asks to keep a compatible reading while the migration lasts and to block the normative uses the legacy format cannot resolve. With `legacy=True` (`--legacy` in `consolidate` and `ready`), `snapshot.load` reads each legacy record as the sheet of its dry-run migration (legacy and proposed state, ambiguities, candidate relations) and keeps it in `snapshot.legacy`, never in `records`. A sheet has no admitted history, so it is not in force and fulfils no conditions: `consolidate` returns it in `legacy` with a warning, `ready` names each legacy milestone in its warnings and a dependency on a legacy record is not satisfied. A legacy ID that repeats one of the profile or another legacy one blocks the load, and a legacy record without an ID of legacy shape leaves it partial instead of being skipped. `consolidate` on a legacy decision ends in `partial`: it is named, but not resolved. Equivalence with the commands of the legacy checker does not mean giving the same result: KBOL reads the same universe with the same legacy state, never reports as ready what the checker does not and explains every difference. Revisit if: the migration of the corpus ends and the option is no longer used.

### Import

Integration imports a legacy record when the request declares it in `imports` (`{ID: {state, valid_from, precision, inherited_authority}}`). The record arrives in the proposal in the contract format, in its initial state and at the same path as its legacy record in the base. The integrator checks against that legacy record that the type is its own, that the target state is the one the dry-run migration gives, that the inherited authority is the same, that the title, description and scope do not change and that the body is the legacy one except for the clause marks, which wrap it, and a "Legacy provenance" section that only says where it comes from and repeats, with their values, fields of the legacy record. It writes an `import` event instead of the creation event, with the provenance (path and base revision) and the legacy state read from the base, the date with its precision and the inherited authority; it does not fabricate a ratification. What is imported is in force with that authority, and `consolidate` shows it (`inherited`). The approval covers the import: the digest of an imported record includes what the request declares, without changing that of any other record or the published vectors.

The guard (`kbol.importing`) compares the body without the marks and ignoring whitespace, because the marks require blank lines around them and a split may redistribute line breaks; no word may change. The provenance is regenerated from its fields and must match. No text of the imported record may be new: every string appears in the legacy record or is a fixed text of the migration (it starts with "not extracted" or with "not stated in the legacy record", or is "the tasks in the body"), and the same holds for the IDs of its relations. A legacy record that is unreadable in the base makes the base inconsistent and blocks every integration, also those that do not touch it: it fails closed, and the installation keeps its legacy records readable while the migration lasts.

During the migration, a reference to a record still in the legacy format resolves with a warning, not with an error: the target exists, even if it is not in force and does not satisfy dependencies. A reference to an ID that does not exist is still an error. Integration loads the legacy records of the folder to be able to tell them apart.

## Validity and dependency queries

- **Succession between amendments.** Two decisions in force that replace or repeal the same clause are in conflict unless one declares `depends_on` towards the other; then the one that declares it is in force. Amending another clause of the earlier one is not declaring succession, and a mutual dependency does not decide either: the result is `NORMATIVE_CONFLICT`.
- **Retirement.** An amending decision whose validity ended, or that a full successor supersedes, leaves its target clause in `no_rule`: the earlier text is not reactivated. A `supersedes` cycle leaves every decision in the cycle ambiguous, whatever the order of the query.
- **Full succession.** A decision stops being in force, and its `status` becomes `deprecated`, as soon as a successor that supersedes it comes into force. That the successor is later replaced or expires does not revive it: if A falls to B and B falls to C, C is in force and A is still not in force. Restoring A requires a new decision that says so.
- **Validity of a decision.** `full` if its clauses are in force with its own text, `partial` if one is replaced, repealed or in conflict and another is still in force, and `not_in_force` if none is in force, also when all are repealed.
- **Proposals.** They are identified by the state at the knowledge cut-off, not by the current header, and returned apart as non-binding, additions included.
- **Validity without a start.** An imported event with a null `valid_from` does not decide whether it is in force: `AMBIGUOUS_TIME`.
- **`completed_with_evidence`.** Fails closed (`INSUFFICIENT_EVIDENCE`) as long as there is no record of checks per criterion, like `available_with_integrity`: the integrity check exists as a command (below, "Source integrity"), but queries over a snapshot do not read the disk or the store and do not use it.
- **Ready milestones.** A milestone is ready if its last step at the cut-off is `authorized`, the validity of that step covers `valid_at` and all its dependencies are satisfied.
- **Loading the snapshot.** Only records valid in canonical mode enter. An invalid record, or an unreadable file (no header, invalid YAML or not UTF-8, because it could be a record), leaves the query `partial` (exit 3); only generated `index.md` files and readable files whose `type` is not of the profile are skipped; a repeated ID or a forbidden cycle leaves it `blocked` (exit 2). In a git revision, paths are resolved from the root of the repository.

## Work links

Local relations so that a memory or a note can follow the work up to what is in force: a milestone `closes` and `advances` questions, `tests_hypothesis` hypotheses (the contract reserves `tests` for the hypothesis that tests a clause of a decision) and `produces` any record, with an optional anchor; a plan `relies_on` decisions. Work fields: `owner` of the milestone (person or role, like that of the question), `evidence` of the milestone and of the question (paths, commits and outputs, as text) and `implementation` of the decision (`complete`, `partial`, `pending` or `not_applicable`), separate from its state. All are free under mutability: changing them does not reopen a closure or an authorization, because they do not change what is in force. `impact` follows them and `query` shows them; for a person, `query` also lists the milestones and questions owned by them or by a role they hold (at the `valid_at` cut-off, or with no end date if none is given), and whether they are still open. Tasks are not copied into the person. Revisit if: the contract defines work relations.

## Fingerprints and drift

Integration and the bootstrap store in `<first folder>/_fingerprints.json` the SHA-256 fingerprint of the text of every record they write, with normalised line breaks, in the same commit. A proposal cannot touch that file. `kbol drift` recomputes the fingerprint of the records with history, from disk or, with `--staged`, from the git index, and lists those that do not match or have none, with the path of their last integrated version if `--canonical-branch` is given. It warns, it does not block: it ends with 0 even if there is drift, with one exception: if it checked no record or left out one that could not be read, it ends `partial` (3), because what was not examined does not prove there is no drift; with an inconsistent base it ends `blocked` (2), like the queries ("Zero examined and local check"). It is not a signature: whoever edits on purpose can recompute the fingerprint, so it detects carelessness (a hand edit that leaves relations unconnected), not attacks. Records that existed before fingerprints appear without one until their next integration.

With `--canonical-branch` (and without `--staged`), `drift` also looks at the history of that branch: from the first gate commit (committed by the integrator or the bootstrap), it lists in `commits_outside_flow` the first-parent commits that change the records folder without coming from the gate; one from the integrator must carry the `Operation-Id` trailer. What precedes the first gate commit is not evaluated and is declared in the coverage, as is an unreadable branch or one without gate commits. It warns and does not block. It recognises the gate by the committer's email, which anyone can imitate: like fingerprints, it detects carelessness, not attacks. It is complemented by `tests/test_single_gate.py`, which counts in `kbol/` the git commands that move references (`update-ref`, `commit-tree`, `push`, `merge`, `rebase`, `reset`, `cherry-pick`) and only admits them in `bootstrap`, `integrate` and `propose`, with their exact number.

## Packaged skills

The KBOL skills (`kbol` and `add-document`) live in `kbol/skills/<name>/SKILL.md` as package data and travel in the wheel. `kbol export_skills DEST` writes them to `DEST/<name>/SKILL.md` (all of them, or those in `--skills`) and inserts, right after the YAML header, a comment with the installed KBOL version. That way an installation that pins a version receives the skill that describes that CLI and not a hand copy of another. It only overwrites files that carry that mark; if any of the targets exists without it, it writes nothing and ends `blocked` (2). The copies in `.claude/skills/` of this repository are the export of the current version, and `tests/test_export.py` checks it: changing a skill or the version requires exporting again. The skill is edited in `kbol/skills/`, never in the exported copy.

## Zero examined and local check

| Choice | What the contract fixes | Concrete form | Reason | Revisit if |
|---|---|---|---|---|
| Operation that examined nothing | An operation that does not cover its scope is not `completed`; the envelope declares the coverage | Ends `partial` (3) with a warning: `ready` without milestones, `consolidate` with missing IDs, `citations` without rows, `drift` without checked records or with one that could not be read, `migrate` without any proposed legacy record and `context` without records in the scope. `citations` on a folder that does not exist ends `failed` (1) | A 0 over an empty set reads as "all in order" when in fact nothing was looked at | A consumer needs to tell "legitimately empty" from "empty by mistake" without reading `warnings` |
| Result of `verify` | The result of a check is not success if it failed or is unknown | `failed` (1) if the check fails and `partial` (3) if its result is unknown | A failure cannot end with the same code as a success | — |
| Local check | Nothing | `tools/check.py` runs static analysis, the suite on Python 3.10 and 3.14, the tests of `tools/di` in their own project (skipped with `--quick` or `--no-di`, and it says so), and installs itself as a `pre-push` hook with `--install-hook`, which is not installed by default. Static analysis of `tools/di` is left out. `tests/test_documentation.py` checks that the documentation matches the code: modules, commands, cited paths and the policy of an installation | The check has to be able to run on the integrator's machine; continuous integration runs the same command without `tools/di` | — |

Limit: the check only proves the local machine. Nothing forces running it if the hook is not installed, and whoever pushes can skip hooks. The behaviour changes this introduces are recorded in [the breaking-change notes](breaking-changes.md).

## Support query

| Choice | What the decision fixes | Concrete form | Reason | Revisit if |
|---|---|---|---|---|
| What a support is | `based_on`, `dependencies`, the sources in `sources` and the fact citations of the body | Each pair (field, reference) is reported once, with its field; a reference in two fields appears twice. `dependencies` only counts in a synthesis, as in `references`. `depends_on`, `amends`, `affects` and `authorized_by` are not supports. A malformed mark in the body is reported in `body` and in the warnings | It is what holds up the content of the record; `depends_on` is already evaluated by `ready` with its typed condition | A consumer needs the work edges |
| Situations | `in_force`, `not_in_force`, `undetermined`, `missing`, `legacy` or `no_validity` at both cut-offs | A single rule, `dependencies.in_force_at_cutoff`: a source is in force if it is registered and no successor (`supersedes`) came into force; a fact, if it is accepted, its validity covers `valid_at` and no successor came into force; a decision or a clause, according to the consolidation. `not_in_force`: no admitted history, not on record yet, not accepted, expired, replaced, repealed or without a rule. `undetermined`: `AMBIGUOUS_TIME`, inconsistent history, normative conflict or a successor whose validity is not decided. `missing`: the ID or the anchor do not exist. `no_validity`: types without an effective state, with their state at the cut-off | Dependencies and support cannot disagree on what is in force | — |
| Summary per record | Not fixed | `broken` if any support is `not_in_force` or `missing`; otherwise `undetermined` if any is `undetermined` or the body could not be read; otherwise `intact`, or `no_supports` if it has none. `legacy` and `no_validity` do not break on their own, but are listed, with one exception: a `no_validity` support whose state at the cut-off is `retired` does break. Without `--ids`, legacy records are named and not examined, and the query ends `partial` | What is not known is not presented as intact or as broken | A legacy record should break once the migration ends |
| Cited synthesis | Reports its state at the cut-off | `no_validity` with its state; its own supports are not walked from whoever cites it, they are read in its own entry | Avoids walks and cycle guards | Breakage needs to propagate through chains of syntheses |
| Comparison | With a second pair of cut-offs, what changes and the chain that explains it | `--before-valid-at` and `--before-known-until`; the missing one is the later one. Each change carries the situation before and after and an `explanation`: the chain and the origin of the clause, the successors, or the transition (last state event at the cut-off) | A late correction or an expiry are explained without new text | — |
| Output | Only flags and does not block | 0 with broken supports; 3 if it examines no record or a requested ID does not exist, like `consolidate` | A broken support is resolved by whoever owns the record | — |
| Evidence in `query` | The same supports and the same rule; a support that is not in force leaves the evidence insufficient | Sufficient only if the summary is `intact`; otherwise `INSUFFICIENT_EVIDENCE` with the reason for each support | Existing is not enough | — |
| Name | `support`, not `backing` | `support` | `citations` already declares the "semantic backing of the citation" as not evaluated; this query looks at validity, not meaning | — |

Change in dependencies: a fact whose successor has a validity that is not decided no longer satisfies `accepted_and_in_force` (`AMBIGUOUS_TIME`); before, it was taken as in force with a warning.

## Domain vocabulary

| Choice | What the decision fixes | Concrete form | Reason | Revisit if |
|---|---|---|---|---|
| Relation `defines` | A decision declares terms; each entry names its clause, the term, its class, its description and, if any, its aliases (C1) | List of closed objects `{clause, term, class, description, aliases?}` in a decision. `clause` is an anchor of its own body; `term` and each alias, one line; `class`, only `entity_class`. The schema rejects a clause that is not in the body, a term or alias repeated in the record, and one that carries, case-insensitively, the name of a type, field or relation of the contract (C7). It is content: it enters the digest and does not change in a closed decision | Uses the consolidation, replacement and ratification that already exist, like `vetoes` | The contract adopts an equivalent relation |
| When a term is in force | When its clause is in force at the cut-off with the text of that decision (C1) | Resolved with the consolidation (`consolidate._Query`): the decision is in force at both cut-offs and its clause is `in_force` with its own origin. A replaced, repealed or ruleless clause, or a retired decision, leaves the term retired if no other definition in force covers it, also as an alias | A term is exactly as much in force as the rule that defines it | — |
| Undetermined | Ambiguous validity, conflict or two different definitions in force (C5) | Also, a term or alias that is at the same time the name of another term. It is not in force: the query flags it with its reason and its uses, and the gate treats it as undeclared | Two names that resolve to different places decide nothing | — |
| Closed world | From the moment the first term of a class is in force, for the whole installation (C2) | Also closed if a term may be in force but its validity is not decided (when in doubt, fail closed) and after all terms are retired (a retired term is still flagged in its uses). The scope of the defining decision does not limit the reach of the term | What is not known is not presented as free | Vocabulary per scope is needed |
| Scopes | Those of the active roles of the policy; a scope without a role is flagged when validating the base (C3) | `scopes` of the roles whose last step at the knowledge cut-off is `active` and whose validity covers `valid_at`. They are compared literally: `KBOL` and `kbol` are different scopes | The failure is seen before an authority fails | — |
| What is checked | An undeclared term is flagged with its uses; it does not invalidate or exclude (C2) | `kbol vocabulary` checks the records that are on record at the cut-off and not retired, rejected or cancelled: entity classes (`undeclared`, `undetermined`, `retired_in_use`, resolved by alias) and scopes (`scopes_without_role`). Ends with 0 even with findings; 3 if it examines no record or there are legacy records, which are named without checking. In an open world, `coverage.not_evaluated` says so | Flagging does not break whoever queries, and a retired term does not take any closed record out of the base | — |
| Integration gate | The vocabulary of the final tree is in force; an effect that takes an entity to `active` is blocked if it uses a term not in force at its start of validity; the rest enters with the warning (C4) | After the checks of the final tree, without changing any earlier one: for each effect to `active` of an entity, the vocabulary of the final tree with `valid_at` at the `valid_from` of the effect and what is known at integration. An undeclared, undetermined or retired term blocks with `INVALID_SCHEMA`. The receipt warns of the class and scope of each touched record and of each entity whose term stops being in force through the operation (C6). The approval package blocks the same way and lists the same findings | The decision and its first use can enter together; and changing the vocabulary requires accepting a decision, which is already decisive in both modes | — |
| Cut-offs of the gate | The term must be in force at the start of validity of the effect (C4) | The world is taken as closed if it is closed at integration or at the start of validity of the effect, and the class must be in force at both cut-offs. An import that brings `defines` is decisive | The start of validity is chosen by whoever proposes: dating the activation before the first definition cannot open the world, and what fixes the vocabulary requires approval also in the decisive-only mode | Retroactively activating an entity older than the vocabulary is needed |
| Change of class of an active entity | The effect that activates an entity is blocked if its class is not in force (C4) | It is also blocked for an already active entity to change its class to one not in force at integration | Without it, activating with a declared class and changing it later would be activating in two steps with one not in force | An installation needs to fix the class of active entities before declaring the term |
| Ambiguous definition | An undetermined term counts as undeclared at integration (C5) | An undetermined definition keeps the world closed for all classes, not only for its term; the reason for the block names the undetermined definitions | If it is not known what is in force, it cannot be claimed that the world is open: fail closed | The ambiguity of a term often blocks activations unrelated to it |

**Limits.** There are only entity classes: scopes are not vocabulary and there are no hierarchies, inference or predicates. There is no vocabulary per scope: a term applies to the whole installation. `impact` does not follow `defines` yet: a change to a term does not reach the entities that use it as impact, except for the receipt's warning. Only the step to `active` is blocked: an entity already active that changes its class to a term not in force enters with the warning. That a decision narrowing or retiring a term writes its migration (C6) is not checked. Proposing a term to the general vocabulary (C8) is outside the engine.

## Commands for an installation's hooks

The knowledge logic that every installation repeated in its hooks lives in a command, `kbol session FOLDER --event <event> --installation <json>`. The installation's adapter reads the event from its harness, locates the binary, calls the command with the event's `cwd` and wraps the output in that harness's format.

| Choice | What the decision fixes | Concrete form | Reason | Revisit if |
|---|---|---|---|---|
| Shape | Hooks call a CLI command | A single command with `--event` (`start`, `stop`, `commit`), in the `session` module | The three events share the root, the configuration and the task; one command per event would repeat their arguments | An event needs arguments it does not share with the others |
| Root | Nothing | `FOLDER` is any folder of the working tree; the command goes up to its root with git, which in a worktree is the worktree's. A relative `--installation` is relative to that root | The hook receives the session's `cwd`, not the root, and runs from the main clone | — |
| Configuration | Nothing | From the installation it reads `records_folder` (text, several separated by commas; mandatory), `scope` (mandatory on `start`), `budget` (integer, 30 if missing), `canonical_branch` (`main` if missing) and `legacy_format` (the default format if missing), on top of what the context package already reads. With the declared format it reads the records of the package, the drift on start and on commit, and a badly declared one makes the command fail before reading anything. It is read from disk | These are the keys a start-up hook needs | Another installation needs a scope per task |
| Task | Nothing | Without `--task`, the branch: whatever is not a letter, digit, period, hyphen or underscore becomes a hyphen, it starts with a letter or digit and has at most 100 characters; `no-branch` with a detached head. `feat/x` and `feat-x` share task and handoff | It is the id under which the session keeps its handoff, without anyone telling it | Two live branches share a task |
| Clock | Queries do not read the environment clock | `start` without `--valid-at` uses the current instant and declares it in the envelope's `valid_at`. No other command reads it | A start-up hook has no other instant to give | — |
| `start` | Start-up context and drift | The package of `context` and the drift on disk, with a single load of the records. The envelope carries the whole package, the drift, `reused` and `fingerprint`; `--text`, the presented package and one line of drift. `completed` (0), `partial` (3) or `blocked` (2) according to the package, and `partial` if no record with history was checked; drift does not change the code. With a partial or blocked package the text is still given and says so | Two commands over the same records read them twice; and a blocked package cannot exit with the same code as a partial one | — |
| Stored result | Measured latency per event | `.kbol/session/start-<task>.json` stores the result with a fingerprint and is reused while it does not change: KBOL version and files, configuration, task and its handoff, head, canonical branch, working tree (status, differences with the head and content of untracked files) and the cut-off, which is the given `--valid-at` or, if not given, the day. A failure is not stored | Loading and validating the base takes seconds and most start-ups change nothing | The base grows until computing the fingerprint costs more than the load |
| After compacting | Handoff before compacting | No command of its own. `start --origin compact` adds to the text the task's own commits and its changed files, from the handoff's git facts | A snapshot taken before compacting repeats what the handoff recomputes afterwards, and the previous event cannot inject anything into the session | Something must be kept that git and the handoff do not have |
| `stop` | Check on stop | Validates in `proposal` mode the `.md` files of the records folders with uncommitted changes whose `type` is of the profile; with `--paths`, only those, which is what the session edited. An unreadable file counts as rejected, just as it leaves a load partial. `failed` (1) if any is rejected, `completed` (0) if all are valid and `partial` (3) if there were none | With several sessions in one clone, each one answers for its own; and having validated nothing is not having validated | References between records also need checking |
| `commit` | Drift | The drift of the git index, with the folders and the branch of the configuration; `--text`, one line per record that differs from what was integrated. Same codes as `drift`: 0 even with drift | Warns and does not block | — |

**Limits.** The fingerprint does not see files ignored by git. With the cut-off by day, a validity that starts or ends at another hour of the same day is not reflected until the next one, and the `valid_at` that a reused result declares is the instant at which it was computed. Routing is left out: the signal table belongs to each harness and KBOL has no routing model. Locating the binary from a worktree stays in the adapter, and the guard dispatcher (C2) belongs to each installation. `context` keeps its code 3 for a blocked package.

## Handoff: check history

A new run of the same check replaces the previous one in `checks`; the previous one goes to `check_history`, without its full output, which is deleted (`evidence.deleted`), and saving the handoff keeps it. That way a failure followed by a success stays written. The history keeps the last 200.

## Mutability

Besides accepted or rejected decisions and facts, the content of resolved or discarded questions, validated, refuted or retired hypotheses, retired assumptions, closed or cancelled plans, completed or cancelled milestones and retired records does not change. An authorized plan does not change its goal, constraints, authorization or milestones, and an authorized or in-progress milestone does not change its goal, scope, authorization, acceptance, tolerances, checks or dependencies, without a new authorization. The format of a source is immutable and its `access` is a policy change that requires prior authority.

## Authority and integration

- **What is approved.** The person approves the diff of a GitHub PR that compares the expected base with the proposed commit. The requested effects (transitions and validity dates) travel in that diff, in `<folder>/_requests/<operation_id>.json` with `{operation_id, effects}`. Whoever asks for integration only identifies reviews (`{mechanism: github-review, pull, review_id}`): they supply no digests, effects, identities or roles. The integrator computes the digest of each record with its effects and builds each approval from what was verified: actor (`human:<person>`), account, roles actually held, base, instant of the review and revision of the policy.
- **Verifier.** `GitHubVerifier` has the repository and the canonical branch fixed by configuration, and reads the token from `KB_GITHUB_TOKEN`; without it, it is not enabled. It requires the PR to point to the proposed commit, target the canonical branch and compare with the expected base, and its base not to have changed after the approval (`base_ref_changed` or `base_ref_force_pushed` in the timeline). It counts the current stance of each account: its last effective review (approval, request for changes or dismissal; comments do not count) must approve that same commit. An approval withdrawn afterwards does not count, and a review of an earlier commit is `STALE_APPROVAL`. Each review is verified only once per integration, and one cited twice counts as one. The HTTP client does not follow redirects, because urllib would forward the authorization header. Whether GitHub dismisses approvals or not when the base of a PR changes has not been checked against the real service.
- **Capabilities.** `ratify`, in the scopes of the role, for decisions, plans, milestones and the rest of records with a scope; `govern_policy` for adding and changing roles, people and access to sources. The person must be human, active and hold the role at the instant of the review and also at that of integration, because a revocation is revalidated at integration.
- **Root of trust.** Integration asks for the authority of the base policy, so the first role that governs the policy cannot be activated through it. `kbol.bootstrap` does it once: the roles and the person of the root are already on the canonical branch as proposals without history; the person is human, holds all those roles and declares in `identity_ref` the account GitHub returns for the token (`GET /user`, only accounts of type `User`). Two admitted events are written per record (creation and step to `active`) with the evidence `bootstrap-github-user`, in a squashed commit with the `Bootstrap` trailer. It refuses if there is already an active role with `govern_policy`, and also if the folder has other records without admitted history: integration loads the base in canonical mode, so a hand-written proposal would block it; those proposals leave the canonical branch and come back in through integration. The root is taken as established if some role that governs the policy has history, even if it was retired, or if some record carries a bootstrap event: retiring the root does not open a second bootstrap with another account. Before moving the branch, the bootstrap commit is loaded in canonical mode and must load completely; its commits carry their own identity (`bootstrap@localhost`), different from the integrator's. **Limit of the evidence:** the proof is what the process itself obtained from GitHub at that moment; unlike a PR review, it cannot be verified again later. Auditable evidence would be a bootstrap PR approved by that account and checked with `GitHubVerifier`; that is left for when the installation has the approval channel. Like integration, without branch protection on the remote it records the verified account, but does not prevent another one from writing to the branch.
- **Approval package** (`kbol approval_package`). Before asking for an approval, a read-only command builds what the person sees: per record, what changes in the header (without history or projections) and in each clause, the text in force next to the new one when it `amends` another, the effects with their previous state, whether it is decisive and why, its supports and whether they are in force at `--valid-at`, the impact and the digest. The digests come from the same code as integration (`integrate.prepare_request`), which fills in the previous state of each effect before computing them, so they match those the gate recomputes. If the gate would block for something that does not depend on the approval (paths, request, mutability, effects, imports, final record, references or conflicts, with `integrate.final_tree`), the package returns that `blocked` with the same code and reason. The skeleton is a declared approval with the base shown and the digests; identity, session, instant and quote are `null`, because whoever collects the approval supplies them. **Limits:** it does not evaluate the authority or the authenticity of whoever approves, nor the semantic backing of the supports; supports are evaluated in the proposal, without the effects of the same operation; and it does not look at the canonical branch, so if it moves before integrating the gate answers `BASE_CHANGED`. The gate does not change.
- **Proposing from the integrator's clone** (`kbol propose`). The integrator does not write to a checked-out branch, so each installation integrates into a `--bare` clone of its remote. The command walks the whole path with the files of the working tree it is given: it creates the clone if it does not exist (and does not use one whose `origin` is another remote), fetches the canonical branch, writes the proposal as a commit on top of it with git plumbing, with the request if there are effects or imports, and calls the same gate, without changing it. `--until` says how far it goes: `dry_run` (the default) integrates into a temporary branch `dry-run-<op>-<random>`, with receipts in a temporary folder, and deletes it; `integrate` writes the clone's canonical branch and does not push; `push` also runs `git push` without forcing. When fetching it never discards what was integrated and not yet pushed: if the clone is ahead of the remote it proposes on its head and says so (`pending_push`); if they have diverged (someone else pushed first), it blocks with `BASE_CHANGED` and gives the exact command that discards them (`git update-ref` with the previous value), so that a person decides: receipts are kept and what is discarded is redone with a new `operation_id`. An operation already integrated in the clone is finished by repeating the command with the same `operation_id`: if its receipt is there and its commit is on the branch, the disk is not proposed again (the gate would reject it, because the file does not carry the events the gate wrote), the later steps are repeated and, with `push`, it is pushed; the result says so (`resumed`, with a warning). Commands that talk to the remote do not prompt (neither git nor ssh, with `BatchMode`) and are cut off after 300 s. The `operation_id` admits neither `..` nor a reserved Windows name. **The approval is not assembled in the command**: it admits no quote, session or identity, nor assumes them; it receives in `--approvals` the list of declared approvals already given, with the digests that were shown, and it is the gate that checks they are those of what is being integrated. If the gate asks for an approval that was not given, the dry run returns the approval package of that same proposal and ends `pending_approval` (3); whoever collects the approval fills in the skeleton and repeats the command with it. If the content changes in the meantime, `STALE_APPROVAL`. The branch, the folders, the approval mode, the remote and the receipts are not passed as arguments: the installation fixes them, read from `HEAD` as in `verify`. **Limits:** it proposes the files as they are on disk, without checking that the working tree starts from the head of the canonical branch (mutability and the package show what changes); outside the dry run, if a later step fails or the remote rejects the push, what was integrated stays in the clone without being pushed and the command does not undo it: it is pushed with the next operation or with `git push` from the clone, which is why a dry run comes first. Revisit if: the installation moves to an authenticated approval channel, which would bring its own proposal flow.
- **Configuration of `propose`.** Optional, closed `integration` block of the installation: `remote` (URL or path of the canonical remote), `repository` (the name of its local state, `$KBOL_STATE/<repository>/`, with `integrator.git` and `receipts/`), `approval` (`all`, the default, or `decisive`), `after_integrate` (ids of declared `checks`), `views` (globs with `/`, where `**/` crosses folders) and `author` (`{name, email}` of the proposal and view commits; by default `local-proposer`, and never the integrator's or the bootstrap's email). It also uses `canonical_branch` and `records_folder`. Reason: what tells one installation from another is its own data and is versioned with it; the mechanism is the same for all.
- **Later steps and views.** After integrating, and before pushing, `propose` runs in order the checks of `after_integrate` in a temporary checkout of what was integrated, with the runner of `verify` (no shell, with a time limit and `{python}`) and without line-ending conversion; what a step generates stays in the index, so the next one sees it as tracked. What they change has to be a view: a path that matches `views` and, inside a records folder, only an `index.md`, which is what the record loader skips; that way a step never writes a record, the fingerprints or a request. The views that change go in their own commit on top of the integration's (`kb: views after <op>`), with the declared author. If a step does not end with its expected code, or changes something that is not a view, the command ends `blocked` and does not push. The steps also run in the dry run. Reason: an installation with generated indexes and its own checker needs to regenerate and check them before pushing, and that is not the core's business. **Limits:** the views commit does not go through the gate and has no receipt; what runs is what is on the integrated branch, not what is in the proposer's working tree; views are written as regular files (`100644`), without executable mode or symbolic links. The dry run does not change what was integrated, but it may create the clone and move its branch up to the remote, and it leaves loose objects until the next `git gc`.
- **Every integration is authorized.** Every touched record needs a valid approval, even a proposal without effects. The ratification is stored as an event where there are effects or a policy change; in the other records, the authorization stays in the commit's `Reviews` trailer.
- **Writing.** The canonical branch must exist with that exact name, not be a symbolic link and not be checked out in any worktree. The expected base and the proposal are given as full SHAs. The proposal can only touch records of the profile inside the folder and its request file; renames are checked at both ends. The commit is squashed onto the base, without importing the history of the proposal, and carries the trailers `Operation-Id`, `Request-Sha256`, `Base`, `Proposal` and `Reviews`. The branch is updated by compare-and-swap. Git processes receive a whitelisted environment, without the token or inherited `GIT_*` variables, and literal pathspecs.
- **Conflicts at integration.** They are looked for in the final tree at every instant at which the acceptance of any decision, new or existing, comes into force, because the set of decisions in force only grows at those instants. A conflict that the operation introduces or worsens (new candidates on the same clause) blocks; one that was already in the base and the operation does not touch is reported in the receipt, without holding up work unrelated to it.
- **Receipts.** They live outside the canonical tree, in the directory given, one per `operation_id`. By convention, the local state of each installation (integrator's clone, receipts, copies and store) is grouped in `$KBOL_STATE/<repository>/`, by default `~/.kbol/<repository>/`; `integrate` and `bootstrap` do not fix paths and receive them from the operator, and `propose` applies the convention with the `repository` the installation declares. A previous receipt only counts if its commit is on the mainline of the branch and comes from the integrator; its base, proposal, records and impact are rebuilt from that commit. If it is missing, the operation is reconciled from that commit. The same `operation_id` with another request is rejected. **Limit:** the integrator recognises its commits by the committer email and the trailers, which anyone with write permission on the canonical branch can fabricate. That guarantee depends on only the integrator writing to the branch, which is exactly what branch protection on each installation's remote must enforce; without it, neither receipts nor reconciliation prove more than the content of the branch.
- **Impact.** It follows `depends_on`, `based_on`, `dependencies`, `sources`, `challenges`, `tests`, `derived_from`, `resolved_by`, `authorized_by`, `holds`, the work links and the `<fact ref>` citations of the body, up to ten hops. A record that changes in the same operation does not appear as affected: it is already reviewed in it.

## Non-conforming mechanisms

These choices do not lower the contract: they describe mechanisms KBOL offers knowing that they do not meet a requirement, for installations that accept that by their own decision and declare it in their matrix as a capability not available.

- **Declared approval** (`kbol.declared`). The person approves in a conversation and the agent passes to integration their declared identity (`declared:<alias>`, which is the `identity_ref` of their person record), the session, the instant, the literal quote, the base they were shown and the digests of what they were shown. It does not meet the admitted approval of KB-DPP implementation: the proof is not checked against any identity or trusted service, so anyone with access to the repository could write an approval in someone else's name, and RES-02 can only be shown in part. The proof always says so (`authenticated: false`) and `consolidate` lists the declared ratifications of what is in force. What is checked is the same as with any channel: that the approved digests are those of what is integrated (otherwise, `STALE_APPROVAL`), that the base shown precedes that of the integration and that the person is human, active and holds the role in the base policy. The approval is kept in full in the receipt (`approval_details`) and, where there are effects or a policy change, in the ratification event; the `Reviews` trailer carries its identifier, a hash of what was quoted. Revisit if: the installation moves to an authenticated channel.
- **Approval of decisive changes only** (`integrate(..., approval="decisive", actor=...)`, `--approval decisive --actor` in the CLI). The default mode, `all`, is the contract's. In `decisive`, approval is only required to accept or reject a decision; to authorize, close or cancel a plan or a milestone; for changes to people, roles and access; and for an import that carries `amends`, `supersedes` or `resolved_by`, because it fixes what replaces or closes what. The rest (a new proposal, a relation, starting a milestone, resolving a question, an import that only translates) enters without approval. Every event integration writes carries the operation's actor (`human:…`, `process:…` or `client/model`); the ratification also carries, in its approval, whoever approves. The mode and the actor enter the request fingerprint, the receipt (`approval_mode`, `actor`, `decisive`) and the `Approval` and `Actor` trailers. It does not meet KB-DPP authority: what is not decisive changes without anyone with authority approving it. Revisit if: the installation needs to control every change.
- **Declared bootstrap** (`kbol.bootstrap`, `declaration`). The root person declares in a conversation that they are, and the bootstrap activates the root with their declared identity, the session, the instant and the quote, without `GET /user`. It does not meet the verified root of trust: nobody checks that whoever declares is that person. The evidence of the events says so ("declared, not authenticated") and the receipt keeps the declaration with `authenticated: false`. The root is established just as with GitHub: there is no second bootstrap through any channel. Revisit if: the installation moves to an authenticated channel.

## Calibration sample

`tools/calibration/sample.py` reads the receipts of an installation, gathers the records that entered without approval in the decisive-only mode and writes a sheet with a deterministic sample (ordered by the SHA-256 of operation and ID), to review whether something should have been escalated. It only reads and records nothing. With nothing to sample it exits with 3 and says so: having no sample does not show that what was integrated is right. It does not use the impact to choose cases; the sample is only a deterministic draw. Revisit if: the cases with the greatest impact need to be prioritised.

## Source integrity

The contract's `integrity` operation ("Integrity and updating") was reserved for sources and not enabled. `kbol integrity` enables it in part: it checks, it does not remember.

| Choice | What the contract fixes | Concrete form | Reason | Revisit if |
|---|---|---|---|---|
| What is compared | Own cryptographic fingerprint of each original and derivation; originals are not normalised | The `sha256` of the sheet against the SHA-256 of the bytes at its `location`, as they are | — | — |
| Locations | Not fixed | `store:sha256/<fingerprint>` (object of `--store`), `git:<40-character SHA>:<path>` (blob of that revision) and, without a scheme, a path relative to the root (file of the working tree). Any other (a URL, an absolute path, one that leaves the root) stays `unchecked` | They are the three that installations use; a location that another machine cannot open cannot be checked | An installation keeps originals in another service |
| States | Matches, altered, missing or unchecked, with a cause | `matches`, `altered`, `missing` and `unchecked`, with `cause` in all but the first. `missing`: the path is not in the working tree or in the anchored revision. `altered`: the bytes have another fingerprint, or the store location names a fingerprint that is not the sheet's | — | — |
| What could not be looked at | An access failure is unchecked integrity, not proof of tampering | `unchecked`: the store was not given, the object is not in this machine's store (it is local state and is not synchronised), the revision is not in this clone (shallow or not fetched) or is not a full SHA | In a clone a vanished revision cannot be told from an unfetched one; when in doubt, no accusation | The store becomes shared: a missing object would be `missing` |
| Result | A code describes the cause and the state, the operational result | `failed` (1) with `INTEGRITY_BROKEN` if any source is altered or missing; otherwise `partial` (3) with `INTEGRITY_UNCHECKED` if any was left unchecked; `partial` also with no source at all or with records that did not load; `blocked` (2) with an inconsistent base | Broken and unchecked do not end the same way: a pipeline may tolerate the second and not the first | — |
| Which records | Sources | Those of type `source` in the folders, read from disk as in `drift` (with history and proposals), retired ones included | A retired source still backs what cited it | — |

**Limits.** It does not store the last valid check nor checks periodically: each run looks again and declares it in `not_evaluated`. Queries do not use it: `available_with_integrity` still fails closed and "source integrity" stays in its `not_evaluated`. `citations` keeps its own reading of fingerprints, which only looks at the cited sources. A `location` in prose ("paper file") is read as a path from the root and comes out `missing`: a source without checkable content needs its own scheme.

## Documentation links

`kbol links` applies to any Markdown in the repository, whether or not it is a record, the rule that a reference must be resolvable. It is not a contract operation.

| Piece | Choice | Why |
|---|---|---|
| What exists | What git sees under the root and is still on disk: what is versioned and what is new and not ignored, with the case of the index. Outside a git working tree it ends `failed` | A link counts if whoever clones can follow it; Windows is case-insensitive and GitHub is not |
| What is checked | The `.md` files of `--folder` (by default, the whole root). Targets are looked up in the whole root | Checking a folder does not break its links out of it |
| Link | Markdown links and images, inline or by reference, outside code blocks and inline code. A path starting with `/` is read from the root; `?query` is ignored | An example is not a link |
| Anchors | Those of headings, with GitHub's rule (also `-1`, `-2` for repeated headings), `id=` in any tag and `name=` in `<a>`. The `<clause id="C1">` mark is therefore an anchor: `DEC-….md#C1` resolves | It is what GitHub makes navigable |
| Errors | Target that does not exist or is written with a different case, fragment its `.md` does not have, repeated explicit anchor and absolute local path | — |
| Not checked | External links, targets outside the root, fragments of files that are not Markdown and links written in HTML | Beyond what the repository can answer |
| Installation | Optional `links` block of its configuration: `exclude`, folders or files that are not checked (literal copies of third-party documents), and `debt`, list of `{document, target}` of broken links in documents that are no longer rewritten | A closed record is not edited to fix a link |
| Debt | It does not count as an error and is listed in `debt_used`; debt that no longer fails is reported (`debt_surplus`) without changing the result | Debt can only go down |
| Result | `failed` (1, `MISSING_REFERENCE`) with any broken link; `partial` (3) if it checked no document or one is not UTF-8; otherwise `completed` | It validates, like `validate`: what is broken is not a warning |

Revisit if: an installation needs to exclude by class of document and not by folder, or its own rules on what may link to what.
